# Dataset card — tool input schema fidelity (v2, HF-router era)

> **v2 run of 2026-07-05, tier expansion 2026-07-06, OpenAI GPT-5.6 refresh 2026-07-14, Anthropic `claude-opus-4.8` added 2026-07-16, OpenAI `/v1/responses` arm + `inkling` added 2026-07-18, `kimi-k3` (Moonshot native) added 2026-07-19, `kimi-k3-hf` (the same model on the HF router) added 2026-07-27** — 5,160 rows, 25 model-arms over 24 distinct models (11 opens on HF + 14 natively-served: three tiers per vendor, OpenAI at two generations, Anthropic plus its prior-generation flagship, Moonshot's Kimi K3 — which is the one model measured on **both** arms), 3 arms × 20 trials/cell, input role, `pin_drift = 0`, 13 `error` rows (<0.3%). The paired **output-role emission study** (can a model *author* an object conforming to these schemas?) is a separate study, not yet published — its rows were split out of this dataset on 2026-07-06.

## What this dataset measures

Whether models honor JSON Schema 2020-12 keywords (top-level `oneOf`, `const` discriminators, `if/then`, `prefixItems` tuples, `$ref`/`$defs`, enum varieties) when **calling** a tool: each of the six demo tools' verbatim `inputSchema` (see `../schemas.json`) rides as the forced tool's parameters, and the returned arguments get a five-way verdict per trial: `honored` / `dropped` / `invalid` / `rejected` / `error`. This is the production MCP path — SEP-2106 made this vocabulary legal in `inputSchema`, and the model is exactly the party that must conform to it when it emits a tool call.

**Headline findings:**

- **Six models are perfect on input** — `deepseek-v4-flash`, `kimi-k2.6`, `glm-5.2` (all on deepinfra), `inkling` and `kimi-k3-hf` (both on **together** — the non-deepinfra host now has two perfect open models, which independently strengthens the cross-host appendix's point that "perfect" is a `(model × serving host)` property; added 2026-07-18 and 2026-07-27) and `gemini-3.5-flash` (native, raw `parameters_json_schema` field) honor all six keywords, 20/20 per cell (`kimi-k3-hf`'s `create-payment` cell is 19/19 served — one rate-limit `error`) — **and all six OpenAI models join them on the `/v1/responses` arm** (their recommended endpoint; on the chat.completions arm they stay at 0.83 behind the top-level-`oneOf` request-time rejection). (One asterisk on the Gemini cell: the title-vs-const probe below shows 3.5-flash's `get-enum-selections` pass is *reconstruction* — Google's transport hides the branch consts from every Gemini generation, and 3.5-flash re-derives them from the `default` + option order.)
- **Top-level `oneOf` (`lookup-record`) is the hardest keyword, and it fails two different ways.** Anthropic and OpenAI **request-time reject** it deterministically (20/20, HTTP 400 — on *every tier*, and for OpenAI on *both generations*: the GPT-5.6 family rejects with the same wording; Moonshot's chat-shaped endpoint, by contrast, accepts it and `kimi-k3` honors it 20/20); `qwen3.6-35b` (20/20) and `qwen3.5-397b` (16/16 served) emit **invalid args** for it instead; `gemma-4-31b` splits 13/7. For OpenAI the rejection is **endpoint-scoped**: it belongs to `/v1/chat/completions` — on the `direct-responses` arm the same verbatim schema is accepted and honored **20/20 by all six OpenAI models** (and every other tool is 20/20 there too: the whole OpenAI × Responses non-strict grid is a perfect 720/720).
- **The tier axis separates the API gate from model skill.** Anthropic's `oneOf` rejection is byte-identical across Fable 5 / Sonnet 5 / Haiku 4.5 — it happens at the API, not in the weights — but **Haiku 4.5 alone** also fails `create-payment` (the `const`-discriminator union) with invalid args 20/20: a model-skill failure. OpenAI's three tiers are indistinguishable — and so are its two generations: the GPT-5.6 refresh (gpt-5.6-sol / gpt-5.6-terra / gpt-5.6-luna, 2026-07-14) reproduces the 5.5/5.4 grid cell-for-cell (honored 20/20 on five tools, the same deterministic `oneOf` rejection, 0.83 honored-of-served). Google shows a **generation split**: 3.5 Flash honors all six; both 3.1-line models fail `get-enum-selections` with invalid args 20/20 — and the failure is surgical, not an "enum" failure: the three plain-`enum` fields are perfect 20/20 on both 3.1 models, while the two `oneOf`/`anyOf`-of-`const`+`title` fields (the SEP-1330 titled selects) fail 20/20 by returning the display `title` (`"Wonder Woman"`, `["Salmon", "Trout"]`) instead of the `const` wire value (`"hero-3"`, `["fish-2", "fish-3"]`). The title-vs-const probe (appendix) traces the cause to the transport: no Gemini generation can see the branch consts.
- **Claude (Fable 5 and Sonnet 5) honors `prefixItems`** (plot-point 100%) — the top-level `oneOf` rejection is now Anthropic's only API-level gap on the (non-strict) grid arm. Two Anthropic scopings from the 2026-07-18 probe (appendix): the rejection is **combinator-general** ("input_schema does not support oneOf, allOf, or anyOf at the top level" — a root `anyOf`, or `oneOf` wrapped in `allOf`, rejects identically), and unlike OpenAI there is **no endpoint escape hatch** (everything is `POST /v1/messages`) — only the schema-rewrite one (nest the union one level down, which non-strict accepts).
- **Anthropic's own strict tool use (tool-level `strict: true`, GA — an axis the grid never tested) rejects all six verbatim schemas and decomposes like OpenAI's, but stricter** (appendix, 2026-07-18): four of six first-failures are the envelope (`'additionalProperties' must be explicitly set to false`); with the envelope added, `$ref`/`$defs` is accepted and honored 10/10; the unsupported pieces are `oneOf` anywhere (nested `anyOf` is fine), `if`/`then`, `prefixItems` (**loudly rejected**, where OpenAI tolerates it inertly), and — beyond OpenAI — the value-constraint keywords `minimum`, `maxItems`, and any `minItems` other than 0/1, plus a sibling `type` next to `anyOf` (the inverse of OpenAI's typed-branch requirement). Every tool has a strict-expressible repair honored 10/10 on both models probed — and the strict repair **fixes Haiku 4.5's only model-skill failure in the grid** (the `const`-discriminator union: invalid 10/10 non-strict → honored 10/10 strict).
- **OpenAI `strict` mode rejects all six tools on every tier and both generations** (720/720 `rejected`) — but the blanket rejection is **not six keyword verdicts**. The strict validator reports only the *first* failure, and for four of the six tools that first failure is strict's envelope boilerplate (`additionalProperties` must be supplied and false; `required` must list every property) — which masks whether the keyword under test is even reachable. The decomposition probe (appendix, 2026-07-18) shows: with only the envelope added, `$ref`/`$defs` is **accepted outright** (and honored 10/10); the genuinely forbidden keywords are `oneOf` (anywhere — nested included) and `if`/`then`; `prefixItems` can't be *enforced* (`items` is mandatory and must be an object schema) yet is *tolerated* as unenforced decoration next to a valid `items`; the legacy `enumNames` rides through untouched; and every one of the six tools has a strict-expressible rework (`anyOf` of typed, closed branches; root constructs nested one level down) that the models then honor 10/10.
- **Newly *exposed* by GPT-5.6 (not new with it): the chat-completions endpoint refuses function tools at any non-`"none"` reasoning effort** (HTTP 400, `param: "reasoning_effort"` — captured verbatim by the follow-up probe: *"Function tools with reasoning_effort are not supported for `<model>` in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'."*). The probe (appendix, 2026-07-18) sharpens the original framing three ways: (1) the gate is **not specific to the 5.6 generation** — `gpt-5.5` returns the byte-identical 400 when `reasoning_effort="low"` is set explicitly; what's new in 5.6 is that its *default* effort is reasoning-on, so the gate fires with no reasoning parameter at all; (2) the **schema gate fires before the reasoning gate** (`lookup-record` at default effort gets the top-level-`oneOf` 400, not the reasoning 400), so the grid's deterministic rejection cells are unaffected by the reasoning question; (3) on **`/v1/responses`** — the endpoint the error message recommends — all four OpenAI models accept **and honor all six verbatim schemas**, including the top-level `oneOf` that chat.completions has always rejected. To keep the arm on the same endpoint and request shape as every other row, the harness measures the GPT-5.6 cells with `reasoning_effort="none"` (self-adapting retry in `direct_providers._call_openai`; the applied value is recorded per row in the new `reasoning_effort` column — `"none"` on all 720 GPT-5.6 rows, `null` everywhere else). Caveat: those cells therefore measure the models *with reasoning off*, while every other model runs at its vendor default; given all six OpenAI models score identically, the operating-point difference doesn't change any verdict here.
- **The `direct-responses` arm (2026-07-18): OpenAI is perfect on its recommended endpoint.** All six OpenAI models × all six tools, non-strict, at default (reasoning-on) effort: **honored 20/20 in every cell** (720/720) — including the top-level `oneOf` that the chat.completions arm request-time-rejects 20/20. With `strict: true` the same endpoint rejects all six tools with wording byte-identical to chat (same validator behind both endpoints). Two readings follow: as a *vendor* claim, "OpenAI honors all six 2020-12 keywords" is true on the API surface OpenAI recommends today (tying the perfect opens and Gemini 3.5 Flash); as a *delivery-path* claim, the chat-vs-responses split is the study's sharpest single-vendor flip — same models, same schemas, opposite verdicts by endpoint. Caveat: under a forced `tool_choice` the models usually skip reasoning (608/720 non-strict rows report 0 `reasoning_tokens`; max 298), so this arm measures the endpoint's schema acceptance + the models' fidelity with reasoning *available*, not behavior under heavy reasoning load.
- **`kimi-k3` (Moonshot native, 2026-07-19): five keywords perfect — including the top-level `oneOf` — but Moonshot's API request-time-rejects `prefixItems`.** K3 honors `lookup-record`'s top-level `oneOf` 20/20 on a chat-completions-shaped endpoint — the schema Anthropic and OpenAI-chat deterministically refuse — plus enums/`const`/`$ref`/`if-then` all 20/20. Its one gap is the API's, not the model's: `plot-point` is rejected 20/20 with *"not a valid moonshot flavored json schema … At path 'properties.coordinates.items': items must be an object"* — Moonshot validates schemas against its own flavor and refuses the 2020-12 tuple form (`prefixItems` + `items: false`), making it the **third vendor whose API gates a keyword on the default path** (Anthropic/OpenAI-chat: top-level `oneOf`; Moonshot: `prefixItems`' `items: false`) — and unlike the OpenAI/Anthropic *strict-mode* bans (opt-in axes, see the appendices), Moonshot's gate fires with no strict flag involved. Two operating-point caveats, both per-row recorded: K3's thinking is **always-on** (no off switch exists; only `reasoning_effort="max"`), so unlike the GPT-5.6 cells (measured reasoning-off) these cells measure the model *with* thinking; and Moonshot refuses a *specified* `tool_choice` under thinking — its gate fires **before** the schema gate, the reverse of OpenAI's ordering — so the harness self-adapts to `tool_choice="required"` (equivalent forcing with exactly one tool offered; the sent mode is in the `tool_choice` column, `"required"` on all 120 K3 rows). **The endpoint attribution is confirmed twice over.** First by a same-model control on a *different* model (`moonshot_family_probe.csv`, 2026-07-19): Moonshot's API also serves `kimi-k2.6` first-party, and probed there (thinking disabled, standard forced tool_choice, grid prompts) K2.6 reproduces its deepinfra profile on five tools 20/20 while `plot-point` flips ✓ → **rejected 20/20 with the byte-identical flavored-schema wording**. Then, decisively, by **K3 itself on a second host** (2026-07-27): the HF router began serving `moonshotai/Kimi-K3` on `together`, and the same verbatim schemas over that route are honored **20/20 on all six tools**, `prefixItems` included (`kimi-k3-hf`; its `create-payment` cell is 19/19 served after one rate-limit error). Identical model, identical schemas, one keyword flipping on the endpoint alone — so the ⊘ is Moonshot's request-time validator, **not** a K3 capability gap. This is the study's only same-model two-arm comparison; every other arm pair covers disjoint cohorts.
- **`minimax-m3`'s one gap — `plot-point` invalid 20/20 — is a host artifact, not the model.** The cross-host appendix's failing-cohort run shows the same model honoring `prefixItems` 100% on fireworks-ai, novita, and together; only the pinned deepinfra cell fails. The main-grid ✗ stands as the pinned-host verdict (the measured unit is `(model × serving host)`), but read it as deepinfra's serving stack, not minimax's weights.
- **`gpt-oss-120b` is the weakest open model on its pinned host** — `get-enum-selections` invalid on every served trial (14/14; 6 no-tool-call errors), via the same title-for-const swap the Gemini probe documents. The cross-host appendix shows this one is **host-conditional** (novita and scaleway reproduce the swap; fireworks-ai and together are 100%), and its `$ref` cell is the study's most host-sensitive (40–100% across five hosts — and not even stable in time on deepinfra itself: 65% in the 2026-07-05 main grid, 100% in the 2026-07-19 cross-host re-run; see the re-run note in the cross-host appendix).

## Methodology, conventions

- **honored-of-served** = honored / (honored + dropped + invalid + rejected); `error` rows (rate-limit/transport noise, no-tool-call responses) are excluded from the denominator. In `summary.csv` this is the first-class `honored_of_served` column, with a **served-based** Wilson 95% CI (`hos_ci_lo`/`hos_ci_hi`) — the CI on the *served* count, not on `honored/trials`.
- **accepted** = the provider took the schema and returned a tool call (honored + dropped + invalid). **served** = accepted + rejected (`error` excluded).
- **The two-metric split (`summary.csv`, added 2026-07-21).** honored-of-served pools an API/host gate with a model skill, so `summary.csv` reports both separately: **`accepted_pct`** = accepted / served — did the provider even *accept* the verbatim schema (the SEP-2106 gatekeeping question; a host property, deterministic — it repeats across trials); and **`honored_given_accepted`** = honored / accepted — *given* acceptance, did the model emit valid + faithful args (the model-skill question). They factor the headline metric exactly: `honored_of_served = accepted_pct × honored_given_accepted`. Rank neither the pooled column nor `accepted_pct` as "model quality" — `accepted_pct` is the host's, `honored_given_accepted` is the model's.
- Trials per cell: 20 (`DATASET_TRIALS`). Verdict logic is the Python port of `playground.html`'s `HONORED_CHECKS` (kept in lockstep).
- **Sampling is each vendor's / serving host's default.** No request sets `temperature`, `top_p`, or a seed, so every cell measures the model at the decoding regime its provider ships — which also means cross-vendor comparisons compare default regimes, not one fixed operating point. The one exception the SDKs force: Anthropic requires `max_tokens`, set to 1024 (the demo tool calls are far smaller; no truncation was observed); no other arm sends an output cap.
- **Four grid cells rest on fewer than 20 served trials** (errors excluded from the denominator): gpt-oss-120b × enums (14 served), qwen3.5-397b × top-level `oneOf` (16 served), gemini-3.1-pro × `$ref` (18 served), and kimi-k3-hf × `create-payment` (19 served — a single `429` rate-limit reply) — the study's 13 `error` rows fall entirely in these four cells. `summary.csv`'s **`underpowered`** flag (`served_n < trials`) marks exactly these four; the glyph tables show the honored-of-served verdict without per-cell n, and `summary.csv` carries the full per-cell distributions with `served_n` and the served-based CI.
- **A near-zero `dropped` count is a design property, not evidence that silent flattening never happens.** Five of the six input schemas pin their keyword with `required` branches and closed objects, so a model that flattens the keyword produces arguments that fail validation (`invalid`) rather than valid-but-unfaithful ones (`dropped`) — only `get-enum-selections` (deliberately open) can realistically land there. See `why.md` for the design rationale; 4 of 5,160 rows are `dropped`.
- Prompts (one fixed prompt per tool) favour the schema without restating it: each states the task in one sentence whose values already conform, and `lookup-record`'s adds the study's one explicit structural nudge ("Use whichever single identifier the tool expects") — rates are upper bounds under this favourable phrasing; request-time rejections are deterministic and repeat 20/20. (The uncoached control below re-phrases the tasks naturally; for the other five tools the two phrasings differ only mildly, which bounds how much that control can detect.)
- **`honored` measures structural + keyword correctness, not content accuracy.** The check is: the returned arguments validate against the verbatim `inputSchema` (a real Draft 2020-12 validator) AND the demonstrated keyword is respected (exactly one `oneOf` branch, a 2-element numeric tuple, the right `const` discriminator, `$ref` resolved). It does *not* check that the *values* are semantically right (that the city is actually San Francisco). And two tools hand the model an already-conforming value to place (`register-address`'s ZIP, `create-payment`'s card number), so those honored cells are partly "copies the given value into the right structure," not value-level derivation (the copy-vs-derive appendix probe tested this directly: once the value must be *narrowed* rather than *placed* — a ZIP+4 to five digits — honored can drop sharply, but *fragilely* — it depends on the exact phrasing and the serving host, so it is a caveat on reading those cells, not a stable model property).
- **`rejected` vs `invalid` are different failures.** `rejected` = the provider's API refused the schema at request time (does the provider *allow* the keyword). `invalid` = the provider served it but the model's arguments fail validation (the model filled it out *incorrectly*). `honored` = filled it out correctly. The study measures both questions, separately.
- **On open models, a verdict is `(model × serving host)`, not the model alone.** The adversarial probe (appendix) confirms neither deepinfra nor together (inkling's host) is grammar-masking, so their `honored` reflects the model — but different hosts enforce and break schemas differently, so read an open-model number as "this model *as served by this host*."
- Classification is re-derivable offline from stored `arguments` via `reclassify.py`; `summary.csv` (including the fair-measurement split) is re-derivable from `runs.jsonl` via `recompute_summary.py`. Neither calls a model, and `recompute_summary.py` never rewrites `runs.jsonl`.

## Appendix — serving-host variance (cross-host side experiment, 2026-07-06 + 2026-07-19)

So the catalog says "expect tool calling"; the measurement says "expect it to work to wildly different degrees per host." The catalog is the capability *claim*; this dataset is the behaviour.

**Native (maker) control — GLM on `zai-org`.** GLM is the one model here whose maker self-hosts on the HF router (Zhipu/Z.ai, `zai-org`), so we added it as a native-serving control. So "the model's own maker serving it" is not the ceiling; deepinfra beats the maker on `$ref`. (Kimi and DeepSeek have no maker-hosted HF provider — only third parties serve them there — so no equivalent native control exists on-router.)

### Is a provider grammar-forcing the tool call? (adversarial probe, `probe_grammar.py` → `grammar_probe.csv`)

A natural suspicion: the perfect deepinfra scores might be deepinfra running **constrained/grammar decoding** that *forces* conformance, rather than the model honoring the schema. Test: prompt the model to **violate** each constraint (ask for both `oneOf` branches; a 3-element tuple; a non-enum value). A free decoder complies with the violation → `invalid`; a grammar-constrained one *cannot* emit it → still `honored`.

**Result: no host is grammar-forcing — the scores are the model, shaped by the host.** Told to include both id and name, deepseek-v4-flash on deepinfra emits `{"id": …, "name": …}` (**invalid 20/20**); told to pick "Gandalf", glm-5.2 on deepinfra emits `"Gandalf"` (a non-enum value, **invalid**). A grammar decoder makes both impossible; deepinfra lets them through — so deepinfra is a **faithful passthrough**, its perfect scores are the model earning them. Crucially, **no host is running an output-forcing grammar**: fireworks-ai emits schema-*invalid* args on deepseek's `create-payment`/`create-shipment` (20/20) and rejects others at request time — a grammar decoder could do neither. So where the same model emits exactly one branch on fireworks/`zai-org` but both on deepinfra, that is **not enforcement** — most likely the model on those hosts grabs one value, or the host renders the `oneOf` into a prompt that leads it to pick one. We can't distinguish "model grabs first value" from "host rendering nudges it" from the output; we can only say it's the host (same weights, host-determined), not a grammar. Net: the `honored` numbers reflect the **model**, not a masking decoder — but a verdict is `(model × host)`, because the host's schema handling shapes what the model emits. **Together, `inkling`'s only host, was added to the probe when inkling joined the grid (2026-07-18) and passes the same check**: told to include both id and name, inkling emits both (`invalid` 20/20 — a free decoder), while on the tuple and enum violations it *knowingly refuses* — it plots `[3, 7]` and writes "z=9 cannot be plotted with this 2D tool" into the label (held 19/19, 17/18). So inkling's perfect 120/120 is the model earning it, with no second-provider control possible (Together is the only host serving it). One scope note: `kimi-k2.6` hit an error wall under the violation prompts on deepinfra — no tool call on 20/20 get-enum, 16/20 plot-point, and 14/20 lookup-record trials, with zero invalids on the trials that did serve — so the deepinfra passthrough conclusion rests on deepseek-v4-flash and glm-5.2; kimi-k2.6's own perfect grid cells are not directly cleared by this probe. Full per-cell distributions + example arguments in `grammar_probe.csv`.

### Coaching effect — uncoached control (`probe_uncoached.py` → `uncoached.csv`)

The main grid's prompts hand the model already-conforming values, and `lookup-record`'s adds an explicit structural nudge, so its honored-rates are called upper bounds. How loose is that bound? This control re-runs a **natural, nudge-free** version of each task (the task + data, but no hint about structure — e.g. `lookup-record` becomes "Find the customer account for Acme Corp — its internal id is REC-4417", naming both an id and a name with no "pick one"), so the model must derive the requirement from the `inputSchema` alone. Same arms/hosts as the main grid (opens on deepinfra, closed native); **all 21 models then in the dataset** × 6 tools × 20 trials (the GPT-5.6 trio added by a scoped merge on 2026-07-14; `claude-opus-4.8` (2026-07-16), `inkling` (2026-07-18), and `kimi-k3` (2026-07-19) postdate this control and have no uncoached rows).

**Result: coaching is a tight bound for strong models, a real one for weak models on hard keywords.** Of the 122 comparable (model × tool) cells, **109 (89%) are identical** coached vs uncoached, and **14 of the 21 models are identical on every cell** — eleven of the twelve closed models (all but `gemini-3.1-pro`, whose one moved cell is a single trial; the three GPT-5.6 models are identical on all six tools) plus deepseek-v4-flash, kimi-k2.6, and minimax-m3; four more models (glm-5.2, qwen3.6-35b, qwen3.5-397b, gemini-3.1-pro) moved by only one or two trials in a single cell. Those perfect scores are the model reading the schema, not the prompt: given both an id and a name with no instruction, they still produce exactly one. **But two weaker opens genuinely lean on the coaching:** `gemma-4-31b`'s top-level `oneOf` collapses **65% → 0%** uncoached (it emits *both* id and name, invalid 20/20 — its coached honoring was entirely the hint), and `gpt-oss-120b`'s `$ref` drops **65% → 30%**. So the coached number is not inflated for the models that carry the headline findings, but it *is* a real upper bound for the mid/weak models on the hardest keywords — and the coaching-Δ itself is a useful signal of "reads the schema" vs "needs it spelled out." (Two bounds on the claim: the natural prompts don't actively *tempt* a violation the way the adversarial probe does — where even strong models can be pushed off — so this is normal-use, not stress; and the four `gemini-3.1-pro` cells with no Δ are preview-tier quota errors on the *uncoached* side, not a coaching effect.) Full per-cell numbers in `uncoached.csv`.

### Title vs const — why the Gemini models fail the titled selects (`probe_title_const.py` → `title_const_probe.csv`, 2026-07-13)

The grid's Gemini 3.1 "enums" ✗ has a precise fingerprint (per-field breakdown of `runs.jsonl`): plain-`enum` fields perfect 20/20, the two `oneOf`/`anyOf`-of-`const`+`title` fields failing 20/20 with the `title` substituted for the `const`. Two candidate mechanisms: Google's serving stack degrades the schema before the model sees it, or the model sees both and prefers the label. The probe separates them with three conditions on `get-enum-selections` (native arm, raw `parameters_json_schema` field; `gemini-3.1-pro` + `gemini-3.1-flash-lite` + `gemini-3.5-flash` as control; 10 trials per forced-call cell, 0 error rows):

- **Echo (schema visibility):** unmodified tool attached, calling not forced, "quote the exact allowed values in text." **All three models — 3.5-flash included — quote the titles and never the branch consts, 9/9 trials.** The consts don't survive Google's function-declaration path. (Run with `mode=NONE` instead of `AUTO` and even the control hallucinates placeholder values — NONE appears to hide the declarations entirely.)
- **Baseline (forced call):** 3.5-flash 10/10 honored; 3.1-pro 1/10; 3.1-flash-lite 0/10 — reproduces the grid on both ends.
- **`title` moved into `description`:** identical to baseline for all three models — not a `title`-keyword quirk; the branch values are lost regardless of where the label sits.
- **Consts renamed to self-describing slugs** (`wonder-woman`, `salmon` — words literally present in the prompt): 3.5-flash drops to **7/10**, and its three missed trials split two ways: two invent a slug that is neither const nor title (`"wonder_woman"`), and one echoes the titles on the multi-select (`["Salmon","Trout"]`); the 3.1 models still fail 10/10, echoing the title on the single-select in every trial (bar case-mangled variants like `"wonder woman"`) even though the correct const is now the prompt's own word.

**Conclusion: the transport hides `oneOf`/`anyOf` branch `const`s from every Gemini generation; every Gemini model is guessing the wire value.** 3.5-flash guesses well — it reconstructs `hero-N`/`fish-N` from the visible `default` + option order, which is why its grid cell is ✓ — but the renamed-const condition shows that ✓ is reconstruction, not schema fidelity (a model that saw `"salmon"` in the schema would never invent `"wonder_woman"`). The 3.1 models don't attempt the reconstruction and echo the visible label. This is the **silent-degradation counterpart to the ⊘ finding**: Anthropic/OpenAI reject a schema they can't honor at request time; Google accepts it and serves the model a degraded view. Practical guidance for tool authors: on this path a plain `enum` (+ `enumNames` for labels) survives; the SEP-1330 `oneOf`-of-`const`+`title` pattern silently loses its wire values. Caveat: the echo condition is the model's self-report of the schema it sees — indirect evidence — but the renamed-const behaviour corroborates it independently, and `gpt-oss-120b`'s title-for-const swap on deepinfra (a faithful-passthrough host) shows weak models can also produce the same substitution without transport help, so the transport attribution is specific to the Gemini arm.

### What does `strict` actually forbid? (`probe_strict.py` → `strict_probe.csv`, 2026-07-18)

The grid says OpenAI `strict: true` rejects all six tools, 720/720, every tier, both generations. But strict's validator reports only the **first** failure per schema, and the six first-failure messages split into two kinds: two name the keyword under test (`lookup-record` "'oneOf' is not permitted"; `register-address` "'if' is not permitted"), while four complain about strict's **envelope boilerplate** (`additionalProperties` must be supplied and false; `required` must include every property) — leaving the keyword question unanswered. The probe walks each tool down the failure chain with three condition kinds — `verbatim` (control), `envelope` (only the boilerplate added, keyword untouched), and per-tool strict-expressible repairs — on `gpt-5.5` + `gpt-5.6-sol` (identical cell-for-cell; rejections early-stop after 2 identical 400s, accepted cells run 10 trials):

| tool (keyword) | verbatim | envelope | strict-expressible repair |
| --- | --- | --- | --- |
| `create-shipment` (`$ref`/`$defs`) | ⊘ envelope msg | **✓ honored 10/10** | — (envelope *is* the repair) |
| `create-payment` (nested `oneOf`+`const`) | ⊘ envelope msg | ⊘ "'oneOf' is not permitted" (nested) | `anyOf` + `type` on each bare-`const` branch → **honored 10/10** |
| `get-enum-selections` (enum varieties) | ⊘ envelope msg | ⊘ branch "must have a 'type' key" | same `anyOf`+typed-consts treatment → **honored 10/10** (`enumNames` tolerated verbatim) |
| `plot-point` (`prefixItems`) | ⊘ envelope msg | ⊘ "array schema items is not an object" (`items: false`) | lossy `items:{number}` + `min`/`maxItems: 2` → **honored 10/10**; `prefixItems` *kept alongside* a valid `items` is **accepted** (tolerated as unenforced decoration) → honored 10/10 |
| `lookup-record` (top-level `oneOf`) | ⊘ "'oneOf' is not permitted" | ⊘ same | union nested one level down (`{query: {anyOf: [closed id-branch, closed name-branch]}}`) → **honored 10/10** |
| `register-address` (`if`/`then`) | ⊘ "'if' is not permitted" | ⊘ same | conditional re-encoded as a nested `anyOf` of closed branches → **honored 10/10** |

**Conclusions.** (1) The blanket "strict rejects all six" decomposes into *one* envelope-only case (`$ref`/`$defs` is fully supported), *two* hard keyword bans (`oneOf` anywhere, `if`/`then`), and three schemas blocked by strict's structural rules (`type` mandatory on every branch, `items` mandatory and object-valued). (2) Every ban has a strict-expressible rework that preserves the constraint — strict's closed-world rules (`additionalProperties: false` everywhere) actually make `anyOf`-of-disjoint-closed-branches *equivalent* to the `oneOf` it replaces — except `prefixItems`, whose per-slot typing is genuinely inexpressible (the repair is lossy) though the keyword itself is tolerated inertly. (3) Root-level combinators are banned by the *general* function-schema gate (same wording as the non-strict `lookup-record` rejection), so the root union must change wire shape (`{query: …}`), which an MCP bridge would have to unwrap — schema translation, not just schema tightening. (4) The envelope itself changes semantics: strict has no optional properties, so `get-enum-selections`' five optional selections become required. Net for MCP clients bridging tools into strict mode: it is a **schema-rewriting exercise with semantic costs**, not a flag flip — and the wire shapes it produces are no longer the shapes the MCP server's validator expects.

**Framing note — these repairs are measurements, not guidance.** MCP's position (SEP-2106) is that tools publish standard JSON Schema 2020-12 and clients validate against it directly — that standardization is exactly what makes validation straightforward. Rewriting schemas per provider reintroduces the translation layers the standard exists to remove: it changes wire shapes the server's validator won't accept, silently drops constraints, and forks one tool contract into per-vendor variants. The repair conditions exist in this probe to *quantify* what each vendor's strict mode would demand and where its accepted subset falls short of the spec — the gap is the provider API's to close, not something MCP is telling servers or clients to paper over. Full rows in `strict_probe.csv`; every variant schema is embedded in `strict_probe.meta.json`.

### The reasoning gate + the Responses-API control (`probe_gpt56_reasoning.py` → `gpt56_reasoning_probe.csv`, 2026-07-18)

The GPT-5.6 refresh found chat.completions refusing function tools at the family's default reasoning effort, and the grid's 5.6 cells are measured at `reasoning_effort="none"` — but the original 400 was never preserved (the harness's fallback retried before it could land as a row), and "is this gate new, and what does the recommended `/v1/responses` do with our schemas?" stayed open. The probe (5.6 trio + `gpt-5.5` as the prior-generation control):

- **The gate, verbatim** (one row per model): *"Function tools with reasoning_effort are not supported for `<model>` in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'."*
- **The gate is not new with 5.6** — `gpt-5.5` returns the byte-identical message when `reasoning_effort="low"` is set explicitly. The 5.6 novelty is the *default*: its family defaults to reasoning-on, so the gate fires on a plain request. It bars **every** non-`"none"` effort, not just the default.
- **Gate ordering:** `lookup-record` at default effort gets the top-level-`oneOf` schema 400, not the reasoning 400 — schema validation runs *first*, so the grid's deterministic ⊘ cells are valid regardless of reasoning settings.
- **`/v1/responses`, default (reasoning-on) effort, strict off: all four models honor all six verbatim schemas** — 5/5 per cell, 120/120 rows, including `lookup-record`'s top-level `oneOf`. The chat-completions top-level-combinator gate **does not exist on the Responses endpoint**. (Caveat: with a forced `tool_choice` and these short prompts the models mostly skip reasoning anyway — 95/120 rows report 0 reasoning tokens, max 165 — so these cells show the *endpoint accepts and the models honor* the schemas with reasoning available, not behavior under heavy reasoning load.) *This probe finding was promoted to a first-class arm the same day: the full 20-trial `direct-responses` grid (all six OpenAI models × strict on/off, 1,440 rows) confirms it wholesale — see the Design table and the Results headline bullet.*
- **Strict on Responses:** explicit `strict: true` rejects all six with byte-identical wording to chat.completions (same validator behind both endpoints); with `strict` *omitted*, all six are accepted and honored — the effective default is non-strict.

**Conclusion: OpenAI's schema gatekeeping is per-endpoint, not per-model.** The same verbatim 2020-12 schema can be request-time-rejected (chat.completions), fully honored (Responses non-strict), or rejected again for different reasons (strict on either endpoint) — with the model held constant. This is the v1 "delivery path changes the verdict" finding reproduced *inside one vendor's own API surface*, and it means the grid's OpenAI ⊘ column reads precisely: "chat.completions refuses this schema," not "OpenAI models can't receive it." Full rows in `gpt56_reasoning_probe.csv`.

### Anthropic strict tool use + the combinator gate (`probe_anthropic_strict.py` → `anthropic_strict_probe.csv`, 2026-07-18)

The OpenAI decomposition raised two questions by symmetry: does Anthropic's *own* strict tool use (tool-level `strict: true`, GA, no beta header — an axis the grid never tested) behave like OpenAI's, and is Anthropic's top-level-`oneOf` rejection escapable the way OpenAI's turned out to be? The probe (`claude-sonnet-5` + `claude-haiku-4.5`, identical on every gate cell; rejections early-stop after 2 identical 400s, accepted cells run 10 trials):

**The combinator gate is general, and there is no delivery-path escape.** The rejection message names its own scope: *"input_schema does not support oneOf, allOf, or anyOf at the top level."* A root `anyOf` and a `oneOf`-wrapped-in-`allOf` reject with the byte-identical message, strict or not (recorded as the four `combinator-gate` conditions in `anthropic_strict_probe.csv`, 2026-07-20; both models, every trial). And since Anthropic has a single API surface (`POST /v1/messages`), there is no Responses-style endpoint that lifts the gate — the only way around it is the **schema rewrite**: nest the union one level down (`{query: {oneOf: […]}}`), which the plain non-strict path accepts.

**Strict decomposes exactly like OpenAI's — first-failure masking included — but the accepted subset is smaller:**

| tool (keyword) | verbatim strict | envelope strict | strict-expressible repair |
| --- | --- | --- | --- |
| `create-shipment` (`$ref`/`$defs`) | ⊘ envelope msg | **✓ honored 10/10** | — (envelope *is* the repair) |
| `create-payment` (nested `oneOf`+`const`) | ⊘ envelope msg | ⊘ "'minimum' is not supported" | `anyOf` + drop `minimum` → **honored 10/10** (bare consts + `pattern` fine) |
| `get-enum-selections` (enum varieties) | ⊘ envelope msg | ⊘ "'maxItems' is not supported" | `anyOf` + drop `maxItems` + drop the sibling `type` next to `anyOf` → **honored 10/10** (`enumNames` tolerated) |
| `plot-point` (`prefixItems`) | ⊘ envelope msg | ⊘ "'minItems' values other than 0 or 1 are not supported" | `items:{number}` with **no length constraint at all** → honored 10/10; `prefixItems` kept next to a valid `items` is **rejected** ("property 'prefixItems' is not supported") |
| `lookup-record` (top-level `oneOf`) | ⊘ combinator gate | ⊘ same | union nested one level down as `anyOf` (nested `oneOf` is also rejected under strict: "Schema type 'oneOf' is not supported") → **honored 10/10** |
| `register-address` (`if`/`then`) | ⊘ envelope msg | ⊘ "'if' is not supported" | conditional as nested `anyOf` of closed branches → **honored 10/10** |

**Divergences from OpenAI's strict**, both directions: Anthropic additionally bans the value-constraint keywords OpenAI accepts (`minimum`, `maxItems`, `minItems` beyond 0/1 — so "exactly 2 items" is *inexpressible*, making the tuple repair lossier than OpenAI's), bans a sibling `type` next to `anyOf` where OpenAI *requires* `type` inside every branch, and **loudly rejects `prefixItems`** where OpenAI tolerates it as inert decoration — the loud rejection is arguably the better behavior (no silent unenforced keyword). OpenAI-side conveniences Anthropic lacks: none observed beyond the constraint keywords; `pattern`, `const`, `enum`, `$ref`/`$defs`, and the legacy `enumNames` all pass through on both.

**The strict guarantee visibly repairs the weak tier.** Two Haiku 4.5 cells make the payoff concrete: (1) the grid's only Anthropic model-skill failure — `create-payment`'s `const`-discriminator union, invalid 10/10 non-strict (reproduced in this probe's control) — flips to **honored 10/10** under the strict repair; (2) on the nested-union rewrite, non-strict Haiku returns the `query` object as a **stringified JSON blob** (invalid 10/10; Sonnet 5 honors it 10/10), while the strict `anyOf` version is honored 10/10. So for Anthropic the strict trade is: schema rewriting with real expressiveness losses (length constraints, numeric bounds, `if`/`then`, tuples) in exchange for conformance guarantees that measurably fix weak-model output.

The **framing note** from the OpenAI strict appendix applies here with extra force: these repairs are measurements of the vendor's accepted subset, **not** MCP guidance — and on Anthropic even the *non-strict* path forces a rewrite for the top-level union (there is no verbatim-schema escape at all), which is precisely the kind of per-vendor schema forking SEP-2106's standardization on JSON Schema 2020-12 is meant to eliminate. Full rows in `anthropic_strict_probe.csv`; every variant schema is embedded in `anthropic_strict_probe.meta.json`.

### Is the ZIP/card cell a clean derivation measure? A caveat, not a finding (`probe_prompt_v2.py` + `probe_prompt_v2_crosshost.py`, 2026-07-21)

The methodology note above flags that two tools hand the model an already-conforming value to place (`register-address`'s ZIP, `create-payment`'s card number), so those honored cells partly measure "copy the given value into the right structure," not value-level derivation. This probe set out to *quantify* that gap: rerun the tools with a value that must be **derived, not copied** — give the ZIP+4 `98101-4205` where the schema's `if`/`then` wants `^[0-9]{5}$`, so a copier's `98101-4205` fails the pattern (`invalid`) and only narrowing to `98101` honors it — scored by `classify()` plus a value pin, with a field-scoped, format-insensitive `copied_n` diagnostic. An early run *looked* like a broad result (most open models copy the ZIP; two frontier opens hit near-zero). **An adversarial review, then a full strengthening campaign — three more `pattern` tools, the weak closed tiers, per-phrasing logging, and a cross-host control — showed that result does not hold up.** It is fragile along every axis, so the honest conclusion is a *caveat on the grid*, not a standalone finding. The three ways it fails to generalize:

**1. It's ZIP-specific, not "models copy values."** Three added `pattern` narrowings — a formatted phone → E.164 (`^\+[1-9][0-9]{7,14}$`), a lowercase code → `^[A-Z]{3}-[0-9]{4}$`, a dollar price → integer cents — are derived at **100% by nearly every model** (the lone exception: `gpt-oss-120b` copies a *phone*). So the copying isn't a general habit; it surfaces where the given value is *itself a plausibly-valid instance of the concept* — a ZIP+4 is a real postal code, so models treat it as already-correct rather than narrowing it.

**2. It's strongly phrasing-sensitive.** Logging the two phrasings separately (not pooling) shows the same model swinging across the pair, in no consistent direction:

| model (us-zip5) | "…postal code on the mail is 98101-4205" | "…its ZIP+4 is 98101-4205" |
| --- | --- | --- |
| `deepseek-v4-flash` | 60% | **0%** |
| `gemma-4-31b` | 100% | **35%** |
| `gpt-5.4-mini` | 45% | **95%** |

A pooled point estimate hides a 0–100% range, so "model X copies at rate Y" is not a stable quantity (it also explains a 12%→30% move for `deepseek` between two runs — a high-variance cell).

**3. For most models it's the serving host, not the model** (`prompt_v2_crosshost.csv`). Re-running the ZIP derive prompt on each open copier's *other* tool-capable HF hosts — the same `(model × host)` discipline this card applies everywhere else — flips the verdict for most of them:

| model (us-zip5) | deepinfra | other hosts | reading |
| --- | --- | --- | --- |
| `glm-5.2` | 35% | **fireworks-ai 100%, scaleway 100%** (together 10%) | host artifact |
| `gemma-4-31b` | 60% | **together 100%** (novita 55%) | host artifact |
| `qwen3.5-397b` | 60% | **scaleway 95%** | host artifact |
| `deepseek-v4-flash` | 30% | novita 25%, fireworks-ai 40% | **model** — copies everywhere |
| `qwen3.6-35b` | 69% (9/13 served) | scaleway 70% | **model** |

`glm-5.2` — a headline "copier" in the early run — derives the ZIP perfectly on two of its four hosts; its deepinfra copying was the rendering, not the model. Only `deepseek-v4-flash` and `qwen3.6-35b` copy across hosts. The open/closed line doesn't sort it either: the closed `gpt-5.4-mini` copies the ZIP on one phrasing but barely on the other (11/20 vs 1/20 copied — 30% pooled), while the weak-closed `claude-haiku-4.5` and `gemini-3.1-flash-lite` derive it 20/20 on both phrasings.

**What survives.** The grid's `honored` on the ZIP and card cells *does* conflate placing a given conforming value with deriving one — so those cells shouldn't be read as clean `if`/`then`/`pattern` fidelity — but the effect is too fragile (format-, phrasing-, and host-dependent) to state as a property of any model. Two durable curiosities: (a) `gpt-oss-120b` consistently *copies* formatted values (phone, spaced card) and, on the ZIP, returns no tool call on most trials (only 7 of 40 served) — a natural-language reply that `98101-4205` has an extra four-digit suffix the 5-digit field won't take, asking whether to use `98101` (a "notice the conflict and ask" response the honored/invalid/`error` taxonomy files under `error`); (b) `deepseek-v4-flash` copies the ZIP+4 across all three of its hosts, the one clear model-intrinsic case. Full data in `prompt_v2.csv` (per-phrasing) and `prompt_v2_crosshost.csv`. This section stands as a worked example of the card's own `(model × host)` caveat catching an over-eager first reading.
